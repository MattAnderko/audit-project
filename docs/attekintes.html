IT Audit pair project · CIS Docker Benchmark v1.6.0 · branch cis-docker-audit

Audit a Docker stack, fix it, measure it again

A small booking web app runs in three containers: Nginx, Flask and PostgreSQL. It was first deployed with Docker's defaults, with the database set up like the official postgres image's example. We audited it against the CIS Docker Benchmark, hardened it from the audit's action plan, and then ran the same measurements again. REPORT §5.1 - §5.3 AUDITOR REVIEW OF TOOL OUTPUT

When the tool was wrong

Every WARN was checked against docker inspect, config files and mount data, and suspicious PASS results against docker-bench's source code. Four checks out of 117 (2.2, 2.9, 5.15, 5.3) did not match reality. That is why every finding in the report rests on at least one independent piece of evidence.

The 5.4 check also deserves a note: it gives PASS in v1 because it only looks for capabilities that were added. The default capability set was still there. v2 drops all of them with cap_drop: ALL.

Limits of the audit

  • The host is a single-user Linux workstation (Manjaro), not a dedicated server.
  • AppArmor was switched on while preparing the host. Manjaro leaves it off by default; Ubuntu has it on.
  • It is a snapshot of two points in time; it doesn't test whether controls keep working over a period.
  • Auditor and auditee are on the same team, so independence is limited.
  • No interview was held: the team played the sysadmin role, so the interview questions were covered by document review and observation.
  • The application's own source code was out of scope.
  • Publishing the database port in v1 was a convenience choice, not a default, so M-05's severity partly comes from that choice.

New action items

There is no AppArmor finding. With AppArmor active on the host, Docker applied its docker-default profile to every container automatically, so CIS 5.2 already passed in v1. You can see it in docker inspect as "AppArmorProfile": "docker-default".
